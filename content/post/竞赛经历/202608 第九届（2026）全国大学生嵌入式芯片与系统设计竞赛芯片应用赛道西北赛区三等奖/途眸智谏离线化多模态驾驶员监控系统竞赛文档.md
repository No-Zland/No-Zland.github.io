## 摘  要

  

随着中国汽车保有量的持续增长，疲劳驾驶与分心驾驶已成为引发重特大交通事故的核心诱因。当前主流的驾驶员监测系统（DMS）普遍存在网络依赖严重、功能闭环缺失、成本门槛过高等痛点，尤其在隧道、山区等无网络覆盖区域，传统云端化系统完全失效，无法保障复杂路况下的驾驶安全。
本项目针对上述痛点，基于乐鑫 ESP32-S3 芯片，结合边缘 AI 计算与云端大模型技术，开发了一套可灵活切换离线 / 在线模式的驾驶员状态智能监控系统。系统采用 "双从一主" 异构硬件架构，通过 K230 视觉从控、RK3568 交互从控与 ESP32-S3 物联网主控的协同工作，实现了端侧全离线 AI 推理，彻底摆脱对网络的依赖。同时，项目首创在线 API + 离线 POI 缓存的混合服务区检索方案，解决了无网络环境下的休息引导空白，结合分级报警机制与云端大模型个性化建议，构建了 "异常检测 - 分级报警 - 休息引导 - 远程提醒" 的完整安全闭环。
整机优化后成本仅为 800 元，以普惠的成本实现了全天候、全场景的驾驶安全守护，可广泛应用于家用车、营运车等各类场景，为驾驶安全领域提供了低成本、高可靠的 AIoT 解决方案。

  

**关键词**：驾驶员监控系统；ESP32-S3；边缘 AI；大模型；离线监测；AIoT

# 第一章 设计需求分析

  

本章节主要描述面向驾驶安全领域的实际需求，分析当前行业存在的核心痛点，阐述本作品针对这些问题提出的解决方案，以及如何结合乐鑫 ESP 系列芯片与大模型技术，实现对现有产品的优化与创新。

  

## 1.1 行业痛点与需求背景

  

当前驾驶员监测领域存在三大核心痛点，严重制约了安全技术的普及与效果：

  

### 1.1.1 网络依赖导致的场景盲区

  

多数云端化 DMS 系统将 AI 推理任务部署在云端，需要实时上传视频流进行分析。但在隧道、山区、偏远公路等无网络覆盖区域，这类系统会完全失效，而恰恰是这些复杂路况，最需要安全监测的保障，形成了严重的安全盲区。

  

### 1.1.2 功能闭环缺失导致的干预不足

  

现有同类产品大多仅能实现异常报警，当检测到驾驶员疲劳或分心时，仅通过蜂鸣或语音进行提醒，无法为驾驶员提供有效的后续解决方案。驾驶员在长途驾驶中往往不知道附近哪里可以休息，导致报警无法真正干预危险驾驶行为，安全效果大打折扣。

  

### 1.1.3 成本门槛过高导致的普惠难题

  

高端车规级监测系统成本动辄数千元，普通后装市场用户难以承受，导致大量存量车型无法享受到安全监测技术的保护。安全技术无法下沉到普通用户群体，无法实现大规模的普及。

  

## 1.2 竞赛场景适配与技术需求

  

针对全国大学生物联网设计竞赛乐鑫科技赛道的要求，本项目选择**出行安全**这一未被充分优化的场景，基于乐鑫 ESP32-S3 芯片，结合边缘 AI 与云端大模型技术，打造符合竞赛要求的创新应用：

  

1. **硬件要求适配**：采用竞赛指定的 ESP32-S3 芯片作为物联网从控核心，满足芯片选型要求；

  

2. **传感器融合**：融合 GPS 定位、温度传感、视觉感知等多维度传感器数据，实现多源数据融合；

  

3. **大模型对接**：将端侧采集的驾驶员状态与环境数据上传至云端大模型，实现个性化的安全建议生成，满足大模型交互要求；

  

4. **创新场景挖掘**：针对长途驾驶的安全痛点，提出了全场景离线监测与混合引导方案，挖掘出行领域的创新应用。

# 第二章 特色与创新

  

本章节主要描述作品与现有其他技术或应用相比所产生的优势和创新点，重点突出针对竞赛加分项的技术突破与场景创新。

  

## 2.1 全离线监测能力，彻底摆脱网络依赖

  

传统 DMS 系统依赖云端推理，无网即失效。本项目将所有核心 AI 模型均经过 INT8 量化，部署在端侧 K230 的 NPU 上，所有推理任务均在本地完成。即使在完全无网络的环境下，系统依然可以准确检测驾驶员的疲劳与分心行为，保障复杂路况下的安全监测，填补了无网场景的安全盲区。

  

## 2.2 混合模式服务区检索，解决无网引导难题

  

针对无网络环境下无法获取服务区信息的痛点，本项目首创了**在线 API + 离线 POI 缓存**的混合检索方案：

  

- 在线模式下，通过网络调用高德地图 API，实时获取最新的服务区信息；

  

- 离线模式下，调用本地预置的轻量级高速服务区 POI 数据库，通过 Haversine 公式快速计算距离，检索耗时小于 200ms；

系统可自动检测网络状态，无缝切换两种模式，保障全天候的休息引导能力，真正解决了无网环境下的引导空白。

  

## 2.3 多特征融合疲劳检测算法，鲁棒性极强
  

本项目基于106个人脸关键点，融合多维度的检测数据，实现了高精度的状态判定：
  

### 2.3.1 眼睛纵横比 (EAR) 计算
- 每只眼睛使用8个关键点，采用 **bounding box 高宽比 (h/w)** 方法计算
- EAR = (max(y) - min(y)) / (max(x) - min(x))
- EAR < 0.18 判定为眼睛闭合

### 2.3.2 嘴巴纵横比 (MAR) 计算
- 使用12个嘴巴关键点，采用 **bounding box 高宽比 (h/w)** 方法计算
- MAR = (max(y) - min(y)) / (max(x) - min(x))
- MAR > 0.35 判定为打哈欠

### 2.3.3 眨眼检测
- 检测EAR的快速下降-上升过程
- 需要连续3帧闭眼才算一次完整眨眼
- 正常眨眼频率：10-20次/分钟，异常频率也是疲劳特征

### 2.3.4 PERCLOS 算法
- 60秒滑动时间窗口
- 计算眼睛闭合时间占总时间的比例

### 2.3.5 疲劳分数计算 (0-100)
```
疲劳分数 = PERCLOS × 40% + 眨眼频率 × 20% + 打哈欠 × 20% + 头部姿态 × 20%
```

### 2.3.6 医学安全监测能力
系统在疲劳检测的基础上，利用已有传感器数据和新增跌倒检测模型，实现了对驾驶员突发医学状况的监测：

- **跌倒检测**：集成 SDK 预训练 `yolov5n-falldown.kmodel` 模型（640×640），实时检测驾驶员是否因晕厥、癫痫发作等原因突然跌倒或失去平衡；
- **面部异常监测**：基于 106 关键点时序分析，检测面部肌肉抽搐、痉挛等异常运动模式，辅助判断癫痫发作前兆；
- **异常眼动检测**：基于视线追踪模型，检测眼球偏斜、凝视、上翻等癫痫发作特征性眼动；
- **意识丧失检测**：当眼睛长时间保持睁开且头部完全静止时，判定为潜在意识丧失（晕厥/失神发作）；
- **医学紧急分级**：0（正常）→1（异常征兆）→2（跌倒事件）→3（危急状态）四级告警，与疲劳告警并行独立。

### 2.3.7 6色相位OSD实时渲染
系统采用**全关键点绘制**方案（无人脸方框），通过6色相位系统直观反映检测状态：

- **白色（detect）**：人脸检测阶段，ARGB8888缓冲区 + aidemo.polylines/contours 绘制106个关键点
- **蓝色（register）**：人脸注册阶段，拍照存 face_register、训练存 face_database
- **绿色（normal）**：正常状态，EAR>0.18
- **黄色（light）**：轻度疲劳，疲劳分数 25-49
- **橙色（moderate）**：中度疲劳，疲劳分数 50-69
- **红色（severe）**：重度疲劳，疲劳分数 70-100

绘制流程：每帧新建 ARGB8888 缓冲区 → 遍历10分区调用 aidemo.polylines/contours/draw_circle → 单次 copy_from 写入 OSD，避免多次覆盖导致的闪烁问题。

RGB LED 与 OSD 关键点颜色同步变化，提供视觉+硬件双层状态反馈。

通过多特征数据融合，系统在复杂光照、戴眼镜、戴口罩等各类场景下，检测准确率依然可达 92.5%，鲁棒性远超单一维度的检测方案。

  

## 2.4 大模型赋能的个性化安全引导

  

结合竞赛要求的大模型对接能力，本项目将驾驶员的状态数据、驾驶时长、环境温度、位置信息等多维度数据上传至云端大模型，由大模型生成个性化的休息建议。例如，针对不同年龄、不同驾驶习惯的驾驶员，大模型可以推荐不同的休息时长、不同的休息方式，甚至可以根据当前位置推荐附近的餐厅、酒店等配套设施，实现真正的个性化安全服务。

  

## 2.5 极致普惠成本，实现安全技术下沉

  

通过异构芯片架构与 BOM 成本优化，本项目将整机成本控制在 800 元以内，仅为同类高端产品的 1/5。极低的成本使得普通后装市场用户也可以负担得起，让安全技术能够下沉到普通用户群体，实现大规模的普及，真正做到了普惠便捷，符合竞赛的实用型加分要求。

  

## 2.6 完整安全闭环，真正干预危险行为

  

突破传统产品 "仅报警" 的局限，本项目实现了 \*\*"异常检测 - 分级报警 - 休息引导 - 远程提醒 - 医学急救" 的完整安全闭环。当检测到驾驶员跌倒、癫痫发作等医学紧急事件时，系统自动触发红色快闪报警并通知亲属，形成兼顾疲劳安全与医学急救的综合守护。从检测到异常，到分级提醒，到引导驾驶员休息，再到远程通知亲属，形成了完整的干预链条，真正能够从根本上减少危险驾驶行为，提升驾驶安全。

# 第三章 功能设计

本章节主要描述作品根据需求分析所规划设计的各种功能，着重体现这些功能的作用与价值。

## 3.1 全场景驾驶员状态监测

系统通过端侧 AI 推理，实现全天候的驾驶员状态监测，无需依赖网络：
- **疲劳检测**：实时检测驾驶员的疲劳等级，分为正常、轻度疲劳、重度疲劳三个等级；
- **分心检测**：检测低头、侧视、视线偏离、使用手机等分心行为；
- **身份识别**：支持驾驶员身份注册与识别，可针对不同用户配置个性化的检测阈值；
- **环境监测**：实时监测车内温度，异常温度时主动报警，保障车内环境安全。
## 3.2 混合模式服务区检索与引导
系统根据网络状态自动切换检索模式，为驾驶员提供全天候的休息引导：
- 在线模式下，实时获取最新的服务区信息，包括名称、距离、配套设施等；
- 离线模式下，通过本地 POI 数据库快速检索最近的服务区，保障无网环境下的引导能力；
当检测到驾驶员重度疲劳时，系统会自动播报最近的服务区信息，引导驾驶员前往休息。
## 3.3 分级报警与安全干预
系统根据驾驶员的异常等级，触发不同级别的报警与干预措施：

| 等级      | 触发条件        | 报警方式          | 引导动作                        |
| ------- | ----------- | ------------- | --------------------------- |
| 0（正常）   | 无异常         | 无提示           | 无                           |
| 1（轻度预警） | 一级疲劳或短暂分心   | 语音提示 "请集中注意力" | 无                           |
| 2（中度预警） | 二级疲劳或持续分心   | 蜂鸣慢响 + 语音播报   | 检索服务区并播报 "前方 X 公里有服务区，建议休息" |
| 3（重度预警） | 重度疲劳且无视多次提醒 | 蜂鸣快响 + 紧急语音   | 多次推送报警至亲属手机，引导立即停车休息        |
| 4（医学急救）| 跌倒/面部抽搐/意识丧失 | RGB 红色快闪 + 蜂鸣持续 + 语音播报 | 自动停车引导 + 远程通知急救 + 拨打急救电话      |

## 3.4 大模型个性化安全服务

系统将驾驶员的危险状态数据上传至云端大模型，实现个性化的安全服务：

- **个性化休息建议**：大模型根据驾驶员的疲劳程度、驾驶时长、环境温度，生成个性化的休息建议，例如 "您已经连续驾驶 3 小时，建议休息 20 分钟，活动一下颈椎"；
- **智能路线规划**：大模型结合当前位置与驾驶员状态，推荐最优的休息路线，甚至可以推荐附近的配套设施；
- **远程安全提醒**：当驾驶员出现重度危险行为时，大模型可以生成报警信息，推送至亲属的手机端，实现远程监护。
## 3.5 低功耗休眠与远程唤醒

系统支持低功耗休眠模式，当车辆熄火或长时间无人时，自动降低视觉模块帧率、关断 NPU，将整机功耗降至 0.3W，实现超长待机。同时，通过 ESP32-S3 的低功耗蓝牙功能，支持手机端远程唤醒（规划中），用户可以随时查看车辆状态。

# 第四章 系统实现

  

本章节主要描述实现功能所采用物联网技术架构，包括感知层技术、传输层技术、控制层技术、软件开发技术、云应用等，详细阐述系统的实现细节。

  

## 4.1 总体架构设计

  

本系统采用 \*\*"双从一主" 异构硬件架构 \*\*，通过三个核心芯片的分工协作，实现算力、控制与通信的高效协同，整体架构如下图所示：

  

- **K230 视觉从控**：负责图像采集与本地 AI 推理，完成驾驶员状态的检测分析；

  

- **RK3568 主控单元**：负责系统整体逻辑控制、UI 交互展示与语音播报，实现多模块数据的融合处理；

  

- **ESP32-S3 物联网从控**：负责传感器数据采集、GPS 定位与网络通信，实现离线 / 在线混合模式的服务区检索与远程报警推送。

  

## 4.2 硬件系统实现

  

### 4.2.1 K230 视觉从控模块

  

K230 视觉模块是系统的感知核心，搭载 6 TOPS 算力的 NPU，满足本地多模型 AI 推理需求。模块采用 CanMV 开发板，支持 MicroPython 开发环境，可快速实现算法移植与调试。

图 4-1 CanMV K230 AI 视觉开发板

  

该模块支持红外滤镜增强、图像裁剪等预处理，适配车内复杂光照环境，可在白天强光、夜间弱光等各类场景下稳定采集图像数据。所有 AI 模型均部署在该模块的 NPU 上，实现本地全离线推理。

为兼顾医学安全监测，K230 在原有 5 模型管道的基础上，集成了 SDK 预训练的 `yolov5n-falldown.kmodel` 跌倒检测模型（YOLOv5n 架构、640×640 输入），采用间隔调度策略（每 3 帧执行一次）与 DMS 主管道共享 NPU 算力。同时新增 `MedicalMonitor` 模块，利用已有 106 关键点与视线数据的时序分析，实现面部抽搐检测、异常眼动追踪、意识丧失判定等医学预警功能，在不增加额外硬件成本的前提下扩展了安全守护维度。

  

### 4.2.2 ESP32-S3 物联网从控模块

  

ESP32-S3 是系统的通信与感知核心，完全符合乐鑫竞赛的芯片选型要求。该模块搭载 16MB Flash + 8MB PSRAM，满足通信与本地数据存储需求，同时集成了多种传感器：

- **4.3寸 RGB LCD (800x480)**：搭载 FT6336 电容触摸，实时显示驾驶员状态、疲劳评分、GPS、服务区信息与分级告警；


- **NEO-M8N GPS 模块**：通过 UART1 (9600 baud, TX=18, RX=17) 接收 NMEA 0183 数据，实现经纬度定位与车速计算；

### 4.2.3 RK3568 主控模块

RK3568 主控单元是系统的控制核心，基于 OpenHarmony 5.0 (API 12) 系统运行。由于 OpenHarmony 系统底层驱动的限制，RK3568 的 NPU（1 TOPS）无法在鸿蒙环境下正常调用。因此 RK3568 定位于 **北向应用控制中心**，不执行任何 AI 推理，所有视觉算法与传感器采集分别由 K230 和 ESP32-S3 完成，RK3568 通过 USART 串口接收处理后的数据，负责 UI 交互展示、数据融合与分级告警。

RK3568 端共开发了三款独立 APP，均采用 ArkTS（Stage 模型）开发，通过串口接收 K230 和 ESP32-S3 的数据：

**（1）鸿谏·座舱智守（HonJan）** — DMS 主控应用
- 通过 UART 接收 K230 的 ,{...}# 协议帧，获取驾驶员疲劳等级、疲劳分数、PERCLOS、眨眼/哈欠次数、分心状态
- 通过 UART 接收 ESP32-S3 的 ,{...}# 协议帧，获取 GPS 定位、温度、网络状态
- 根据疲劳等级触发四级分级告警（正常/轻度/中度/重度），联动蜂鸣器(GPIO95)、状态指示灯(GPIO154)、RGB LED 和语音播报
- 支持附近休息区推荐（通过串口向 ESP32-S3 发送 POI 查询指令）

**（2）智能仪表盘（SmartDashboard）** — 车载信息显示
- 实时车速表：基于 ESP32-S3 上报的 GPS 坐标变化，通过 Haversine 公式计算瞬时速度
- 驾驶评分系统：将 K230 疲劳分数映射为 0-100 分的驾驶评分
- 行程信息：行驶距离、方向、车内温度
- K230/ESP32-S3 连接状态实时指示

**（3）疲劳事件日志（FatigueLog）** — 事件记录与统计
- 自动记录 K230 上报的每次疲劳事件，包含时间戳、疲劳等级、分数、PERCLOS、GPS 位置
- 本地 JSON 文件持久化存储，支持历史查询与清空
- 今日统计：疲劳次数、最高等级、平均分数
- 事件详情页：完整展示单次事件的 7 项指标
- 支持 TSV 格式导出

三款 APP 共同构成了 RK3568 端的完整北向软件栈，覆盖了 **实时监测 → 仪表展示 → 事件追溯** 的全链路功能。

#### 4.3.1.1 多特征融合疲劳检测算法实现

基于106个人脸关键点实现高级疲劳检测：

**关键点分布（10分区渲染）：**
- 眉毛轮廓：18个关键点（索引43-51, 97-105），使用 aidemo.polylines 绘制
- 左眼轮廓：8个关键点（索引35-42），使用 aidemo.contours 绘制
- 右眼轮廓：8个关键点（索引89-96），使用 aidemo.contours 绘制
- 瞳孔：2个关键点（索引34, 88），使用 draw_circle 绘制
- 鼻部：11个关键点（索引72-86, 77-83），分鼻梁与鼻底二区
- 嘴唇轮廓：20个关键点（索引52-71），分外唇(12点)与内唇(8点)
- 脸部轮廓：33个关键点（索引0-33），使用 aidemo.polylines 绘制

**算法流程：**
1. 人脸检测获取人脸区域
2. 106点关键点检测
3. Bounding box 高宽比法计算眼睛纵横比(EAR)、嘴巴纵横比(MAR)
4. 检测眨眼和打哈欠事件（需连续多帧持续判定）
5. 计算60秒窗口PERCLOS值
6. 多特征融合计算疲劳分数(0-100)
7. 根据分数判定四级疲劳等级（正常/轻度/中度/重度）
8. OSD渲染：ARGB8888缓冲区 + aidemo.polylines/contours 绘制关键点（6色相位系统）

K230 端采用多任务流水线架构，每帧图像依次经过人脸检测→关键点检测→姿态估计→注视检测→分心物检测，跌倒检测模型以 3 帧间隔与主管道共享 NPU 算力。单帧总推理耗时约 135ms，满足实时检测需求。跌倒检测结果与 106 关键点、视线数据的时序分析共同输入 `MedicalMonitor` 模块，综合判断驾驶员是否出现跌倒、面部抽搐、异常眼动、意识丧失等医学紧急事件。所有阶段均使用**关键点绘制**（无人脸方框），通过6色相位系统（白→蓝→绿→黄→橙→红）直观反映检测状态与疲劳等级。

### 4.3.2 混合服务区检索实现

系统实现了自动切换的混合检索机制：

1. **在线模式**：当网络可用时，ESP32-S3 通过 WiFi 调用高德地图 API，根据 GPS 经纬度实时获取最近服务区的信息；

2. **离线模式**：当无网络时，ESP32-S3 调用本地预置的约 100 条全国主要高速干线服务区 POI 数据，通过 Haversine 公式计算当前位置与各服务区的距离，快速检索最近的服务区，耗时小于 200ms；

系统自动检测网络状态，无缝切换两种模式，保障全天候的引导能力。

### 4.3.3 大模型对接实现

  

为满足竞赛的大模型对接要求，系统通过 ESP32-S3 的网络功能，将端侧采集的多维度数据上传至云端大模型：

  

- 上传数据包括：驾驶员疲劳等级、分心状态、连续驾驶时长、车内温度、当前位置经纬度等；

  

- 云端大模型基于这些数据，生成个性化的休息建议与安全提醒；

  

- 大模型返回的结果通过 ESP32-S3 传输至主控单元，通过语音播报的方式呈现给驾驶员；

同时，当检测到重度危险状态时，系统会将报警信息与位置信息通过大模型平台推送至亲属的手机端，实现远程监护。

### 4.3.4 通信协议与数据流

系统内部各模块通过串口实现高效数据传输：

1. **K230 → ESP32-S3**：通过 USART 串口（波特率 115200）直接传输驾驶员状态检测结果。采用 `$DMS,<json>#` 帧格式（参考 `ybUtils/YbUart.py` 的硬件抽象层实现和 `libs/YbProtocol.py` 的帧格式设计思路），JSON 载荷包含 `fatigue_level`、`fatigue_score`、`perclos`、`blink_total`、`yawn_total`、`head_distracted`、`timestamp` 以及新增的 `medical_level`、`medical_type`、`fall_x`/`fall_y`/`fall_w`/`fall_h`（跌倒框坐标）等医学字段。数据在疲劳等级或医学等级变化时立即发送，医学紧急事件不受 1 秒间隔限制，确保急救信号实时到达；

2. **RK3568 → ESP32-S3**：通过 USART 串口传输报警状态，同时接收 ESP32 返回的服务区、温度、定位信息；

3. **NEO-M8N GPS → ESP32-S3**：通过 UART1 (9600 baud, TX=18, RX=17) 接收 NMEA 0183 语句，由 gps_neo.py 解析经纬度与速度；

4. **DS18B20 → ESP32-S3**：通过 OneWire (IO0) 读取温度，由 temp_ds18b20.py 驱动；

5. **ESP32-S3 → 云端**：通过 WiFi + MQTT 3.1.1 将数据上传至云端大模型平台。Broker: broker.emqx.io:1883，订阅 dms/driver/state / dms/alarm/urgent / dms/llm/advice 三个主题，由 mqtt_client.py 基于 raw socket 实现。

## A.4 附录：ESP32-S3 端接收协议说明

K230 通过 UART1（波特率 115200，K230 引脚 9: TXD -> ESP32-S3 引脚 9: UART2_RX; K230 引脚 10: RXD -> ESP32-S3 引脚 8: UART2_TX）向 ESP32-S3 发送驾驶员状态数据。

**帧格式**：`$DMS,{"fatigue_level":2,"fatigue_score":55.0,"perclos":0.35,"blink_total":8,"yawn_total":3,"head_distracted":false,"timestamp":1717200000.0}#\n`

**发送规则**：数据在疲劳等级变化时立即发送，否则每 1 秒间隔发送一次，避免串口拥塞。

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `fatigue_level` | int (0-3) | 疲劳等级：0=正常，1=轻度，2=中度，3=重度 |
| `fatigue_score` | float (0-100) | 多特征融合疲劳分数 |
| `perclos` | float (0-1) | 60秒窗口内闭眼时间占比 |
| `blink_total` | int | 累计眨眼总次数 |
| `yawn_total` | int | 累计哈欠总次数 |
| `head_distracted` | bool | 头部是否分心（低头/偏头超阈值） |
| `timestamp` | float | Unix 时间戳 |
| `medical_level` | int (0-3) | 医学事件等级：0=正常，1=异常征兆，2=跌倒，3=危急 |
| `medical_type` | string | 医学事件类型：`none`/`abnormal_sign`/`fall_down`/`critical` |
| `fall_x`/`fall_y`/`fall_w`/`fall_h` | int | 跌倒检测框坐标，仅在`fall_down`时存在 |
